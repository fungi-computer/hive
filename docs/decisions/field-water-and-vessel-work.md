## Conservation cannot keep the current closed-total invariant unchanged

**Algebra correction accepted after Root's review.** My previous proposal kept
a separate pail exchange ledger and decremented the physical baseline when soil
was removed. That was wrong: deposited water can later leave inside removed
soil. Root's algebra counterexample is initial1kg, deposit10kg, remove5kg:
the former baseline becomes -4kg despite a valid remaining6kg. This also violates
the actual positive `initialTotalKg` admission in `state.mjs:56-57`. This is an
algebra counterexample, not a claimed executed hydraulic fixture.

Keep **one fixed original `initialTotalKg`**, F0, in the volume state across
transfers and geometry removal. Add one signed cumulative `boundaryKg`, b,
positive into that owner's domain and zero at initial stock creation. It includes
**every** transfer across the domain boundary, including water carried out in
removed porous soil. It is non-spendable accounting, not another source inventory.
Internal paired-face flow preserves F0 and b. The physical invariant is:

    W = F0 + b

Let S be the compensated sum of water in the existing exact porous-removal
records (impermeable records contribute zero). Let M count current contained
water plus water-equivalent recipe inputs and actual end-use water sinks, and
M0 count authored initial material water (currently16). With u kg/material unit,
the joined candidate validates:

    b + S + u*(M - M0) = 0
    W + S + u*M = F0 + u*M0

The pail-only net into the field is **derived** as b+S. Do not save it as another
ledger. The actual transitions explain each sign:

| Accepted effect | Change in W | Change in b | Change in S | Change in u*M |
|---|---:|---:|---:|---:|
| Withdraw q kg to pail | -q | -q | 0 | +q |
| Deposit q kg from pail | +q | +q | 0 | -q |
| Remove porous voxel carrying s kg | -s | -s | +s | 0 |
| Remove impermeable voxel / internal flow | 0 total | 0 | 0 | 0 |

Thus Root's example ends at F0=1,b=5,W=6,S=5: the pail net is10kg into
the field, and material water has decreased by10kg. No negative baseline or
second physical stock is needed. F0 never follows the remaining geometry or
the current stock sum. All quantities and cumulative accounting must remain
finite and representable; rejecting an unrepresentable transfer is preferable
to hiding it with a clamp or a new baseline.

### Partial pails require checked portions, not merged identities

Root's concrete case is decisive: a2-unit pail can retain1 unit after hydration,
and the next kettle request needs2. Allowing only a pre-filled deliver phase
does not close this case. Actual source behavior:

- `owner.ts:529-590` (`moveContainerPortion`) does **not** coalesce contents.
  Moving a whole lot retains its ID; splitting leaves the source remainder on
  its original ID and allocates a new destination lot ID. A1-unit top-up beside
  an existing1-unit lot legitimately leaves two lots inside the same pail.
- `held-use.ts` (`sinkHeldPortion`) requires lot.quantity==requested quantity
  and deletes that whole lot. It cannot currently drink1 from a single2-unit
  lot while retaining1. `pourVesselContents` can split one lot through the
  existing move primitive, but cannot atomically pour portions of two lots.
- `progress.ts:3-36` and `validateOperationWater` persist/validate one content
  ID and require exactly one interior lot of exactly the operation quantity.
  `activity.ts` also demands a single source lot large enough for the whole
  draw despite `jobs.ts` checking aggregate source quantity. Fragmentation can
  therefore block both sides even when enough real water exists.

Smallest coherent policy is **fill to the requested amount, then deliver that
amount**, all through the existing vessel work owner:

1. After actual pail acquisition, inspect eligible contained portions through
   the material owner. For target q and available matching contents c, external
   draw is max(0,q-c), never q again and never blindly capacity-c. If c>=q,
   select q of the current contents and proceed without visiting a source.
   The supply union must represent contents-only explicitly; do not require a
   fictional spring reference when no external supply is needed. Eligibility
   and path estimates use the same deficit rule; actual draw rechecks it.
2. Extend the existing material owner to preflight/apply an exact bounded set
   of portions `{lot,quantity}` from one resolved source container to another.
   Require positive integer quantities, unique lot IDs, matching material and
   real source/custody, unclaimed available amounts, sum equal to the requested
   transfer and aggregate destination capacity. Plan every split/new ID before
   mutating any lot. Reuse the existing whole-move/split rule; do not loop
   fallible single moves over live state and leave a partial batch. The field
   inlet similarly appends a real new lot for only the missing quantity after
   the paired physical debit. No destructive merge is needed.
3. Change vessel deliver progress from one `content` ID to checked
   `contents:[{lot,quantity}]`, selected in stable ID order, sum==operation.q.
   These are references to promised portions, not duplicate physical stock.
   Validate each against the actual bound pail and quantity<=available; extra
   unselected contents may remain in that pail. Acquire/draw phases may hold
   existing contents under normal material/capacity rules. Keep one exclusive
   vessel-use binding rather than add a second contents inventory or claim.
4. Held-use pour, consumer sink and field-return debit use that same checked
   portion selection. A true sink may decrement a partially used lot, retaining
   its ID/remainder, and append one checked consumption receipt only after all
   portions pass; remove a lot only when actually exhausted. A pour preserves
   whole IDs or makes the existing lawful split. A return uses the same debit
   rules but does not append a consumption sink. Destination settlement remains
   all-or-nothing for its requested q; only the remainder stays in the pail.

The required example then follows without special hydration/kettle transport:
existing lot A has2; drinking1 leaves A:1 and a1-unit sink; the next kettle2
operation draws only1, creating B:1; delivery moves A:1 and B:1 to the kettle
