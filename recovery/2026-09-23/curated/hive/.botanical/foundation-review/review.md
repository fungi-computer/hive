**Findings, in priority order**

1. **P2, demonstrated gameplay defect: a canceled roof can refund wood onto an unreachable wall cell.** `src/clearing.js:89-92` refunds at the site coordinates. `src/construction.js:35-37,93-102` permits a roof above a finished wall; `src/world.js:41-50` keeps that wall cell blocked, and `src/movement.js:4-6` forbids picking up there. Sol's actual shipped-WASM probe, `.botanical/sol-review-probe.mjs`, ordered wall + roof at (7,5), chopped oak-1, waited for roof construction and canceled it. Output: `wallFinished:true`, `roofRemoved:true`, `strandedWood:1`, `pickupRoute:null`. Numerical material conservation passes while material becomes unusable. Make refund placement own both quantity and physical recoverability, including cancellation when the pawn has moved on to another order. Do not blindly move every remote refund to the current pawn. Preserve delivered/last-work location where needed, or select a legal drop beside the canceled site; if no legal drop exists, retain recoverable site cargo rather than silently stranding it. Prove that the refunded wood can fund subsequent authorized work, not just that the sum is unchanged.

2. **P2, demonstrated UI defect and needless update work: the order list loses keyboard focus during activity changes.** `src/hud.js:23-40` replaces the entire list with `innerHTML` whenever its text changes. In the actual built game, focusing the cancel button during walking then waiting for chopping changed the active element from BUTTON/job-1 to BODY, although the same order remained. `main.js:190-202` also renders HUD every display frame while paused. One observed paused second generated 777 DOM mutations, including 37 writes to the status notice, with tick unchanged at 71. Evidence: `probe-ui.mjs` and `ui-result.json` in this folder. Use a maintained declarative DOM renderer with stable job keys and a cached, immutable HUD snapshot emitted only when displayed values change. My preference is React for the growing DOM panels, using its ordinary external-store subscription. Keep world simulation out of component state/effects and keep Pixi on its own render path. The refactor should delete selector/property wiring, whole-list replacement and the module-global `lastOrders` cache; preserve the focused row and current visual layout. The observed mutation count is a sample, not an FPS or assistive-technology benchmark.

3. **Foundation risk: game vocabularies and state relationships are unchecked.** `package.json:6-13` has tests/build/format, but no typecheck or lint task. `jobs.js:65-87` treats every job except build/chop as rest; `targetFor:196-201` treats every activity except chop/pickup as a site target. These are not current malformed-input exploits: today's in-page producer emits the closed known kinds. They are silent extension traps when the next job is introduced. Add strict TypeScript first around commands, jobs, activities, sites, cargo and content definitions, with exhaustive kind handling. Make active activity/route/work and persistent job/site progress ownership explicit; remove redundant progress/assignment state where callers can derive it. Use one owner for activity completion/interruption/refunds, preserving resumable site/tree work. A new valid kind should force its real handlers to be implemented at compile time. Runtime decoding belongs at an actual future serialized boundary, not around every internal object.

4. **Foundation risk and repeated work: topology has split authority and is recomputed by unrelated readers.** `createClearing` stores rocks/watcher in state, placement reads them, but `world.js:44-45` routes against module constants. It is equivalent in today's fixed clearing; it will diverge for changed/loaded terrain. Use state as authority. `construction-view.js:80`, `hud.js:78`, `clearing.js:188`, roof eligibility and rest selection independently flood rooms/rebuild blocked cells; bed checks also route between entrances/beds. `assignWork:121-127` continues generating paths for later jobs after choosing the first eligible order so it can update their reason strings. Use one derived topology query result invalidated by changes to occupancy/enclosure/roof/bed facts; let all readers reuse it, including repeated frames and pause. The cache is disposable, never a second durable room/terrain model. Separate ordered-job eligibility from expensive status recomputation. Node timings on the actual accepted 17-element home snapshot were about 0.218 ms for `indoors` and 0.265 ms for `shelteredBeds` per call (2,000 iterations, see `topology-result.json`). This shows real work being repeated, not a demonstrated large-world performance limit or browser FPS claim.

5. **Foundation risk: definitions centralize costs but not enough of the building behavior.** `construction.js:12-26` centralizes labels, wood and ticks but special-cases bed footprint. Wall/door/roof tests recur in placement, blocking, shelter and rendering; `index.html` separately authors palette costs. Extend the existing definitions with typed footprints, material inputs and the concrete occupancy/enclosure/render categories these four objects already require. Derive palette/ghost/material text from them. Keep work effects as ordinary typed functions; do not invent a recipe expression language, arbitrary script runner or universal job graph. An item stack needs item ID + quantity + one owner; a recipe needs inputs + output/work requirements. Introduce the actual output/storage/workstation rules with the first workstation, using common hauling and activity lifecycle rather than another copy of `transferWood`.

6. **Long-session risk: diagnostic history grows inside gameplay state.** `clearing.js:59,175-180` retains every submitted command, including rejected ones. Gameplay never reads this history; tests/proof use it. Keep tick-ordered command recording at the session/proof boundary and preserve deterministic replay evidence without growing the live world forever. If product replay/save history is introduced, choose checkpoints/retention for that feature. Do not turn a diagnostic retention limit into a lifetime work-order cap.

**Data structures that earn their place**

- An ordered array remains appropriate for player job priority. Use ID lookup maps/records for entities/sites/jobs when replacing repeated joins, preserving explicit order rather than relying on incidental map insertion order. Do not maintain two mutable copies of an entity.
- A cell occupancy index and shared topology results directly serve placement/path/room queries. Current sets and breadth-first routing are valid for the small finite uniform-cost grid; a heap/A* or hierarchical path system is not justified by these measurements.
- Typed building/recipe/footprint records make the next content additions smaller and remove duplicated facts. A material transfer remains a domain state transition, not an asynchronous task runtime.
- Reservations become a correctness requirement when two workers can compete for the same pile, destination capacity or workstation. The present one-worker design needs no contention protocol. Preserve ID-based relationships now; design the claim/release semantics with the actual second-worker slice.
- Dense chunk arrays, Z traversal links, a full ECS runtime and multiplayer authority are later work. Plain serializable state and fixed ticks help, but do not claim these systems are implemented or that same-build local replay proves cross-machine lockstep.

**Effect and imperative code**

The accepted [App platform ADR](/home/levi/src/Botanical-next/wiki/3-resources/decisions/adr-effect-owned-app-platform-modules.md) explicitly leaves pure calculations/inert data pure and does not require publisher website/UI code to depend on Effect. The [software-shape guide](/home/levi/src/Botanical-next/wiki/3-resources/field-guide/software-shape.md) asks for narrow mutation, boring control flow and libraries that remove ownership. The game has no live network/storage/concurrent service lifecycle today. Keep synchronous fixed-step mutation in its simulation owner. Effect would earn adoption for real save/network/storyteller I/O, cancellation and scoped resources when those responsibilities exist. Do not model simulated walking, chopping, rest or the colony assignment loop as wall-clock Effect fibers/schedules. The eventual SSE arrival remains input, not the simulation clock.

The DOM HUD should become declarative because it already reimplements reconciliation poorly. Imperative retained Pixi sprite/texture updates remain appropriate; its renderer is designed for a retained scene graph. For `drawSites` specifically, separate sprite membership/lifetime from deriving appearance (stage, joins, cutaway, tint and progress) when extending it. That creates a testable visual decision without building a second Pixi reconciler or mechanically splitting functions to lower metrics.

Primary library references checked during review: [Effect resource management](https://effect.website/docs/v3/resource-management/introduction), [React external-store subscription and snapshot requirements](https://react.dev/reference/react/useSyncExternalStore), [Pixi retained render loop](https://pixijs.com/8.x/guides/concepts/render-loop).

**Recommended next implementation slice**

Preserve this exact home demo's behavior and art while fixing the two demonstrated bugs, typing the domain, extending the existing building definitions, unifying/caching topology queries and replacing DOM HUD reconciliation. Keep the current first-ready libcolony responsibility and direct order/activity composition. Prove cancellation recoverability, existing material/pause/replay laws, topology invalidation after place/finish/cancel/chop, stable keyboard focus and quiet paused HUD. Reuse the current complete home/browser proof as the consumer regression after those source changes. Then let one real workstation recipe demonstrate what must become reusable; its new domain effect is legitimate, repeated travel/haul/cancel machinery is not.

It should preserve the art study and verify identical pixels/anchors. It is separate from the job/UI foundation pass; the current ~795 kB shared art bundle warning is not hidden.
