# Excalibur mechanisms worth learning from

Read-only official-source study, 2026-09-08. Every Excalibur link below pins main snapshot `4a23dd1674b1771a88bbbf9e7f20bcd772e264c4`; this is not a release/adoption claim. Selected source copies are retained at `/tmp/hive-excalibur-mechanisms-4a23dd1`. No dependency installation, production change, build, benchmark or browser proof. Root's separate readers cover ECS/query internals and depth sorting; this note studies four other mechanisms and their actual callers.

## 1. Small composable action contracts—useful for presentation

`Action` defines `update(elapsed)`, `isComplete(entity)`, `reset` and `stop`. `ActionQueue` holds pending/current/completed action objects, advances its first pending action once per update, and emits action-start/completion events. `ActionSequence` wraps another queue constructed by a JavaScript callback. `ParallelActions` updates each child and completes when all report complete. `ActionsComponent` delegates to `ActionContext`; `ActionsSystem` updates retained matching components in the Update phase and excludes the pause tag. [Action interface](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/actions/action.ts), [queue](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/actions/action-queue.ts), [sequence](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/actions/action/action-sequence.ts), [parallel action](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/actions/action/parallel-actions.ts), [actual system](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/actions/actions-system.ts).

The useful design is a common small lifecycle with sequence/parallel wrappers. Hive can use that idea for a familiar's gesture followed by a speech flourish, a portal opening with simultaneous light/scale effects, or a short interface animation. Its existing root plan's typed operations can also present a similarly legible composition API.

Do **not** adopt the runtime queue as Hive's durable work scheduler. It stores mutable instances/entity references and sequence-builder callbacks. `toPromise()` appends a `CallMethod` resolving an ordinary Promise; it does not checkpoint work, own quantities, reserve a shelf or survive a restart. Stop/reset is not compensation for a completed pickup. Parallel updates give every child the same elapsed time; they do not establish independent resource ownership. Queue update boundaries also affect timing, so nesting/reassociation is not automatically a lawful transformation of observable action timing. [Actual Promise implementation](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/actions/action-context.ts#L490-L505).

**Recommendation:** learn the composition/lifecycle shape now; implement only when a real presentation sequence needs it. Keep the reviewed serializable job algebra, fixed-step owner and libcolony for world work. No engine/action-package adoption is needed.

## 2. Pools describe lifetimes, not free game objects

`ArenaPool` hands out objects sequentially and reclaims the arena with `done`; it supports preallocation, an optional recycler and detaching explicitly returned objects. `RentalPool` rents/returns individual objects, optionally calls its cleaner, and prevents repeated return of the same object through a WeakSet. Both can grow; arena `maxObjects` doubles at exhaustion and rental capacity doubles when depleted. `rent` defaults to `clean=false`. These are allocation reuse mechanisms, not hard memory budgets or complete ownership validation. [Arena source](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/util/arena-pool.ts), [rental source](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/util/rental-pool.ts).

The real particle caller preallocates 500 `Particle` objects, rents a particle, unparents/configures it, and returns it after deferred scene removal. Its cleaner is the identity function, so correct reuse depends on the caller/configuration covering the relevant old state. `Particle.configure` retains defaults for several omitted values. This study does not claim a reproduced stale-particle bug; it demonstrates why reset must be audited at the caller, not inferred from the word “pool.” [Emitter](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/particles/particle-emitter.ts#L19-L28), [rent/configure/return caller](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/particles/particle-emitter.ts#L130-L209), [particle configuration](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/particles/particles.ts#L86-L150).

Hive's suitable consumers are short-lived particle/render records and measured scratch allocations for overlap/candidate queries. Frame scratch must not escape into HUD facts, async saves or retained render dependencies before reclamation. Individually pooled projectile visuals need one rent/return owner, cleared event handlers/parent/appearance/motion references, and protection against stale references to a recycled slot. A generation handle is one option if slots escape the owner.

A spent arrow's simulation identity and physical inventory history remain ordinary authoritative data. Reusing its visual slot must never resurrect ammunition or turn a different projectile into the old entity. Cosmetic pools may drop excess effects at a cap; authoritative projectile exhaustion needs explicit admission/backpressure or another correctness-preserving storage policy, not silently skipping a shot.

**Recommendation:** later, measured pools with explicit capacity/reset policies for particles/projectile presentation; use small frame scratch reuse when an actual allocation profile justifies it. Do not copy auto-doubling into an alleged memory budget, and do not pool persistent item identities. No pooling rewrite for the tiny map now.

## 3. Separate offscreen graphics from the live simulation

`OffscreenSystem` runs in the **Draw** phase. It compares transformed graphic bounds to the viewport, handles parallax/force-on-screen, and adds/removes `ex.offscreen` with entry/exit events. It still scans its matching entities. `GraphicsSystem` sees that tag, optionally ticks offscreen graphics, and skips drawing; `GraphicsComponent.updateOffscreen` only advances opted-in graphics. `Scene` registers Actions/Motion/Collision separately as Update systems. The reviewed `ActionsSystem` excludes paused entities, not offscreen ones. [Offscreen system](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/graphics/offscreen-system.ts), [graphics caller](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/graphics/graphics-system.ts#L76-L105), [offscreen tick policy](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/graphics/graphics-component.ts#L492-L517), [scene registration](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/scene.ts#L192-L208).

This separation is directly useful for Hive. Culling can suppress grass animation work, particle drawing and sprite submission without stopping fermentation, fire, plants or villagers. Later rendering should first narrow visible chunks/bounds, then decide visible parts; scanning all world entities to mark them offscreen would not solve large-world scaling. Bounds must include tall canopies and upper-level structures whose anchors lie outside the screen.

Do not let gameplay depend on a sprite animation completion callback that only runs while visible. Important timings belong to simulation ticks; purely cosmetic animations can pause offscreen, catch up from an absolute phase or reset on reentry under an explicit appearance policy. Rendering visibility, chunk data residency and simulation activation remain three different decisions.

**Recommendation:** adopt this ownership rule now in the world/renderer contract. Add culling to the retained Pixi scene with its actual bounds and lifecycle when the world lab/large render consumer arrives. No Excalibur culling system import; it assumes Excalibur scene components and does not supply a streaming/offline simulation solution.

## 4. Spatial broad phase beside component queries

`DynamicTree` indexes two-dimensional AABB proxies. It retains padded bounds so small movements can avoid reinsertion, reinserts when a collider leaves that region, and supports overlap and ray candidate traversal. `DynamicTreeCollisionProcessor` uses that traversal, then filters collision groups and calls exact collider ray tests. The tree's traversal can stop on the first matching callback; the reviewed default processor returns the first traversed exact hit unless `searchAllColliders` is requested. There is no distance sort in that path, so “first” must not be assumed to mean nearest. [Tree update](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/collision/detection/dynamic-tree.ts#L210-L286), [query/ray traversal](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/collision/detection/dynamic-tree.ts#L419-L468), [actual query/raycast caller](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/collision/detection/dynamic-tree-collision-processor.ts#L42-L117).

An ECS/component query answers “which entities have these capabilities?” A spatial index answers “which candidates overlap this place or swept region?” Hive needs both kinds of narrowing: eligible Haul workers and supplies from typed/material queries, then nearby/reachable candidates; predators in a habitat and prey in their search region; moving arrows and nearby surfaces. Neither query proves reachability, contact, visibility, authority or available quantity.

For Hive's regular cells, a chunk/cell bucket index is a simpler initial candidate than a dynamic tree; large/tall or continuously moving bounds may later justify a hierarchy. Excalibur's exact tree is 2D: cross-storey arrows still need full world-volume/trajectory narrow phase, swept distance between ticks, and the earliest valid collision along that path. A screen-space AABB cannot decide whether an arrow passed above a floor or through a wall. Use stable IDs/ties after candidate discovery so tree insertion order does not change deterministic simulation outcomes. Index maintenance belongs to the owner of spatial mutation; it is derived state, not another persisted position.

The included `QuadTree.query` also returns region candidates with deduplication, rather than replacing precise intersection tests; its implementation concatenates arrays and uses index searches. An index's presence is not a performance guarantee. Measure candidate counts, maintenance cost and actual overlap density; large overlapping bounds necessarily produce many candidates. [Pinned quadtree query](https://github.com/excaliburjs/Excalibur/blob/4a23dd1674b1771a88bbbf9e7f20bcd772e264c4/src/engine/collision/detection/quad-tree.ts#L173-L204).

**Recommendation:** adopt the query distinction now. Later compare one derived cell/chunk index against bounded brute force on real jobs/nature/projectile fixtures. Keep broad phase replaceable behind a small API; do not import Excalibur physics or promise O(log n) full queries independent of output size.

## Proposed first useful ports

| Timing                  | Hive consumer                               | Take from the study                                         | Keep out                                                      |
| ----------------------- | ------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------- |
| Now, architecture       | Unified jobs and presentation boundary      | Small lifecycle vocabulary; typed composition               | Live action objects/Promises as durable jobs                  |
| Now, design; later code | Large-world render visibility               | Separate Draw visibility and optional cosmetic ticking      | Camera-driven freezing of world simulation                    |
| Later, measured         | Particles and projectile visuals            | Arena versus individually returned lifetime, explicit reset | Reusing persistent ammunition identity, unbounded auto-growth |
| Later, measured         | Local work search, fauna, swept projectiles | Spatial broad phase plus exact checks                       | Component query as proximity, 2D index as a 3D hit test       |

The immediate recommendation is selective use of these mechanisms within the existing Three→bake→Pixi and deterministic-world owners. There is enough useful source here to improve Hive without adopting Excalibur's engine or treating it as proof that the planned world already scales.
