# Colony-control references — source-observed 2026-09-07

This is a compact design reference, not a control-porting prescription. [Bay 12’s current development log](https://www.bay12games.com/dwarves/) is creator-published; its 2009 squad notes are design history, so they establish a durable distinction but not current key bindings. The [DF Labor page](https://www.dwarffortresswiki.org/index.php/Labor) is a maintained community manual, useful for current work-detail behavior but not a primary creator source. [Fluffy’s WorkTab README](https://github.com/fluffy-mods/WorkTab) is primary for that mod only. No game was run for this review.

**Astra product disposition:** Levi explicitly requested Work permissions and
Draft/Undraft with Go here now. References below saying to defer these until
workshops or a later direct-control slice are superseded by that instruction.
Delivery has accepted paused admission/shared designation -> Work panel ->
Draft/Go here as the current correction, ahead of new deconstruction. Start
with actual Chop/Haul/Build columns, not role-group machinery or a nine-rank
priority grid. Settings govern automatic work; a clearly labeled direct order
may override a preference. Gardening, workshops, role presets, patrols, escort,
formations and combat remain later. The reference distinction between joining
a colony, persistent direct control and a one-off priority job is useful now.

1. **Keep admission, drafting, and an immediate order as three visibly different actions.** Bay 12 describes a squad position/individual-order interface and says direct squad orders can be issued to groups or individual members; earlier creator notes say an order activates a dwarf as a soldier and supersedes its schedule until return to routine ([current log](https://www.bay12games.com/dwarves/), [original squad notes](https://bay12games.com/dwarves/dev_2009.html)). In Hive, `recruit` adds a person to a party (`model.ts:15-19`, `orders.ts:12-21`); `direct: true` interrupts current work and moves a job forward (`orders.ts:79-128`); neither is a persistent draft state. Preserve those meanings. A future **Draft** control should change only a home member's temporary command/role availability, show the drafted set and an explicit **Return to work**, and never invite a visitor or change party membership. “Chop now” stays an immediate order, not the draft button.

2. **Make tactical override have a target, lifetime, and visible release.** The DF source distinguishes scheduled patrol/station/off-duty/training from player orders that break the schedule, and associates an order with a squad or position rather than a disposable person instance ([Bay 12 squad notes](https://bay12games.com/dwarves/dev_2009.html)). For Hive, a later direct-control slice should show `Drafted → station/escort/attack target → return to ordinary work`, including the target cell and cancellation outcome in the actor and order views. It should support a selected group and an individual subset. Do not infer formations, combat AI, patrols, or the exact DF station radius from the cited material; those are not current Hive requirements.

3. **Use work permissions to answer “may do this,” not to silently replace job choice.** DF work details expose named labor sets with `Everybody`, `Only selected`, and `Nobody`, and show worker skill/specialization alongside membership; workshop/occupation assignment can also grant eligibility ([community manual](https://www.dwarffortresswiki.org/index.php/Labor)). The transferable UI is a small named role/work-detail view with an explicit effective-permission explanation, e.g. “Sedge may build because Home builders includes her,” rather than a dense per-person priority spreadsheet. Hive currently has only party/selected-actor job scope and a routine flag (`model.ts:8-30`), so keep that for the two-person home. Add durable work permissions only when there are several recurring job kinds or workshops to explain. DF’s exact overlapping-detail and specialization rules are evidence of complexity to avoid copying wholesale.

4. **Separate a placed designation, a queued workshop request, and the worker who executes either.** Bay 12’s creator log describes work orders created through a task filter or a workshop, with material/workshop availability and conditions visible; it also emphasizes suggested conditions and order ordering ([official work-order notes](https://www.bay12games.com/dwarves/)). Thus a Hive workshop should first have a local queue/bill with input, output, count, and condition, while the scheduler later assigns eligible people. A wall/bed blueprint remains a world site and a Chop rectangle remains a designation. This avoids presenting a workshop queue as “draft Rowan to craft forever.” Current `build` already creates a site/job and `chop` creates a target job (`orders.ts:109-145`); there is no workshop domain yet, so no generic production panel is justified now.

5. **Reveal fine-grained controls after the colony has a reason to use them.** WorkTab’s author exposes per-task priorities only by expanding a work type and warns that detailed priorities can create deadlocks; its scheduler also shows that priority state can be time-scoped ([WorkTab README](https://github.com/fluffy-mods/WorkTab)). Apply the interaction lesson, not its RimWorld implementation: current Hive can keep the roster’s “Now/Next” and target commands (`hud.jsx:555-560,718-754`). When workshops and several workers arrive, add an expandable role row with effective permission, current task, blocked reason, and a reset-to-default action. Do not start with nine ranks, schedules, or automatic labor policy.

6. **Carry active storey through every tactical and designation confirmation.** This is a Hive requirement rather than a claim about a specific DF UI: cells already carry `level` (`model.ts:6`), but screen picking is ground-only (`camera.js:28-35`, `art/scale.js:32-40`). Before upstairs work, no UI should imply upper-floor drafting or area commands work. At that milestone, a selected-storey indicator must accompany the actor/target, preview, order receipt, and camera conversion; cross-storey selection needs an explicit policy. The references establish that direct and scheduled work need separable state, not a ready-made multi-floor interaction scheme.

The immediate product consequence is modest: label the existing two Chop actions as **direct selected people** versus **shared designation**, retain Recruit as an invitation/admission action, and reserve Draft for a real future state with a release action. No source, scheduler, or UI changes were made here.
