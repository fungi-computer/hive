# Caps house-style adoption audit

Scope: source-observed at `199350851c6a80897d1e66378e2ad9a5878853f4`. This is a small host integration, not a new game design system. The HUD already uses Caps `Button` and `Checkbox`; preserve the game’s state, commands, placement, overlay geometry, and art colours while adopting the maintained Caps/Stipe house style.

## The useful correction

1. **Use one compiled CSS entry.** [`hud.jsx:12-13`](../../src/hud.jsx) imports both `@fungi.computer/stipe/styles.css` and `@fungi.computer/caps/styles.css`. Stipe’s public export is raw Tailwind v4 input (`@import "tailwindcss"` and `@plugin "daisyui"` in `node_modules/@fungi.computer/stipe/styles.css`); this Vite host has no Tailwind transform configured. Caps’ public `styles.css`, by contrast, resolves to compiled `dist/styles.css` and its source imports Stipe before its own components. Remove the raw Stipe import, retain the compiled Caps import once. This is a packaging compatibility correction, not a reason to add Tailwind or copy package source.

2. **Use the maintained dark house preset at the HUD boundary.** There is no `data-theme` in current `src`; Caps’ own workbench’s `Surface` sets `data-theme` at its boundary ([`examples.tsx:91-106`](../../../Botanical-next/packages/caps/workbench/examples.tsx)), and its removable CSS limits itself to layout while using semantic variables ([`workbench.css:1-11`](../../../Botanical-next/packages/caps/.ladle/workbench.css)). Put `data-theme="mocha"` on the HUD host, using the maintained Stipe/Daisy dark preset and its semantic foreground/surface/typography rules as-is. Delete the old green/gold token remapping and serif heading paint from [`style.css:1-13`](../../src/style.css) when they only style the HUD; leave coordinate/pointer geometry, game semantics, and canvas art colours to the host. This makes the first joined rendering visibly Caps/Stipe instead of rebranding the old visual system.

3. **Delete the competing generic control and surface paint, retain game layout.** [`style.css:32-57`](../../src/style.css) paints every `button`, including Caps `.btn`; later scoped rules such as `.roster button` ([`158-166`](../../src/style.css)), `.time-controls button` ([`145-150`](../../src/style.css)), and `.command-bar button` ([`547-554`](../../src/style.css)) override its size/background/pressed state again. Remove those visual declarations, the old panel/surface paint at [`222-231`](../../src/style.css), and HUD-specific serif/type colour paint as the corresponding Caps variant/size and Mocha semantic tokens take effect. The generic input accent at [`58-60`](../../src/style.css) and checkbox margin rules at [`567-569`](../../src/style.css) should likewise yield to `Checkbox` except for necessary label layout. Keep `#hud` pointer-event restoration ([`82-92`](../../src/style.css)), absolute anchoring/responsive rules, roster image sizing, target coordinates, and panel/command-bar placement; Caps does not own any of that.

4. **Use the primitives already present before adding blocks.** `Panel()` and `Target()` are positioned game surfaces ([`hud.jsx:448-464`](../../src/hud.jsx), [`687-757`](../../src/hud.jsx)); a generic `Card` cannot replace their coordinate ownership. Keep them and reduce their surface paint only once the scoped tokens look right. Set explicit Caps variants/sizes on the existing buttons: primary for commits such as Recruit/Chop now, secondary or outline for alternate commands, and ghost/small for the existing close, pause, zoom, order-up, and menu controls. `IconButton` is a later optional fit only for those already icon-only controls: it requires an actual icon node plus the existing accessible label, so it should not turn text controls into symbols. Keep native `Checkbox` for Routine and Cutaway ([`584-600`](../../src/hud.jsx), [`974-982`](../../src/hud.jsx)); neither needs a new state owner. The existing native `<meter>` has correct semantics and is not a mandatory `Progress` migration.

## Smallest joined proof

On one normal HUD scene, show the compiled Caps entry with `data-theme="mocha"` and no old generic button/panel/type paint: a selected Build button, a disabled Rotate button, a primary Chop now action, an outline/secondary Queue chop action, and both checked/unchecked Cutaway/Routine controls. Tab to a close or zoom control to verify its visible focus, then activate it and verify the existing HUD command still fires. This proves the actual house surface/foreground/typography, priority, disabled/pressed/focus states, native checkboxes, and pointer-event overlay ownership together; no new interaction model is required.

The retained strength is that Caps remains presentation-only: [`Button`](../../node_modules/@fungi.computer/caps/dist/components/button.js) forwards native props and [`Checkbox`](../../node_modules/@fungi.computer/caps/dist/components/checkbox.js) remains a native input, while `hud.jsx` continues to own model projection and `send` effects.
