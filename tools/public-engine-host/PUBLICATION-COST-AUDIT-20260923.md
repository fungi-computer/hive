# Public host publication cost audit

The local two-client v3 fixture does not support a host-side projection shortcut. The host already selects authenticated, nonretired, matching pack/world recipients before calling `observationPayload()`, and builds that shared payload once per publication. Any retained projection therefore belongs in the session observation owner, where its input dependencies can be checked.

The measured projection dominates recipient encoding: in the 40-publication host-ledger run, projection build was p50 20 ms / p95 37 ms (max 41 ms), while socket encoding and send was p50 2 ms / p95 3 ms (max 4 ms). Eligibility selection was p50 0 ms / p95 0 ms (max 0 ms at local workerd timer resolution). These are host wall-time samples; projection includes session observation work and is not an isolated measurement of any one engine operation.

The workload was `colony-framework-proof-256-100-v3`, driven to sequence 40 and restart-checked at sequence 41 with two live authenticated local workerd WebSocket clients. Across 40 delivered-publication samples, 38 had two eligible recipients and 2 had one; clients received 41 and 40 complete observation frames. The encoded-byte p50 was 363,958 bytes across recipients per publication. Eighty attempts with no eligible recipient were excluded from delivery distributions and counted separately; their eligibility scan was p50 0 ms / p95 0 ms (max 1 ms) over 157 socket candidates. This excludes empty-recipient attempts rather than treating them as zero-cost sends.

A second identical two-client v3 run used temporary opt-in timers inside the observation owner to split that projection cost. Across its 40 eligible publications, stage p50 / p95 was: `projectPresentation` 5 / 11 ms, Whistle 2 / 3 ms, physical render facts 2 / 4 ms, pack visual projection 3 / 6 ms, inventory decoration 2 / 4 ms, work/activity decoration 2 / 3 ms, terrain 1 / 1 ms, and cues 0 / 0 ms at local workerd timer resolution. Overall host projection in that run was p50 18 / p95 38 ms (max 48); socket encoding/send remained 2 / 3 ms. The stage timers do not account for all surrounding observation assembly, so their percentiles should not be summed as if they were a per-sample decomposition. The 40 samples comprise 38 publications for two eligible recipients and 2 for one; both clients received 41 / 40 observation frames, and autonomous restart advanced sequence 40 to 41.

Inventory and work decoration together account for about 4 ms by adding their stage medians. That is not enough evidence to add another memo owner: a correct validator would still need to check visible entity IDs plus material, task, position, attempt and pack-activity dependencies, and there is no measured proof that those checks cost less than the existing 2 / 2 ms median decoration work. Keep the decision pinned as **defer decoration memoization**. Existing presentation projection uses dependency validation and is the largest single measured stage; do not add another cache until hosted/client evidence after the air-capture work shows a larger repeatable owner-level opportunity.

For warmed committed steps 20–39 (20 samples), SQL execution/read wall was p50 2 ms / p95 3 ms (max 5 ms). The Durable Object transaction API, timed through resolution after commit, was p50 50 ms / p95 68 ms (max 83 ms). One alarm set was issued per step; its measured local API duration was p50 0 ms / p95 0 ms (max 1 ms). Alarm lateness was p50 0 ms / p95 1 ms. The cold first 20 steps are excluded from warmed quantiles; they contain startup and a transaction outlier. These are local workerd costs, not Cloudflare hosted SQL billing or service measurements.
