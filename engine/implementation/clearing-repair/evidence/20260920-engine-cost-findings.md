## Strongest findings

1. **The valuable physical/durable skeleton already exists. Preserve it.** `world.rs:4578` deliberately accounts work before movement so arriving cannot earn labor retroactively; `:4594` invokes the one native planner. `work_candidates.rs:97` retains joint matching with bounded lazy route verification (32 routes,8 matching passes,8 admissions); typed Deferred is distinct from NoPath (`route_query.rs:116`). `supply_allocation.rs:56,74` enforces exact source/incoming capacity and restore relations. Authored writes cannot mint physical components (`authored_entities.rs:196,207`). Region candidate execution/capture/accept is one resident lifecycle (`region-program.ts:158,170,193`). Existing `colony-trees.test.ts:19` covers real travel, earned work, cancellation, preserved trunk, restore, re-designation, exact log output and no duplicate output. Existing SQLite Region tests check failed receipt rollback and retry (`src/engine/region/region.test.js:67,158,414`); these were READ, not rerun in this study.

2. **Every positive tick repeatedly re-counts the whole world.** `world.rs:2838` clones all IDs and for every entity walks every registered schema, materializing values and weighting them. Called unconditionally in `advance_batch` at `:4535`, then unconditionally at the end of `advance_construction` (`construction_work.rs:1117,1164`) even with zero working construction. Numerous per-mutation calls add more scans. Cost scales at least O(entity count × schema count) per pass, unrelated to changed state. This is source evidence, not measured attribution. Owner-maintained record weights/dirty accounting with a slow reference check would preserve capacity law while avoiding whole-world recounts.

3. **Incremental SQL records still mean whole-state capture and near-whole-state writes.** Native rollback staging uses `save_records` (`world.rs:4478`); Region `execute` saves after every command (`region-program.ts:178`); browser Worker also captures accepted state after each step (`worker.ts:163`). `snapshot_entities_json` walks every entity/schema (`world.rs:3999`) and serializes ONE entity JSON image. `record_bundle.rs:120` slices that image into256KiB byte chunks. `kernel-records.ts:144` copies all records and reconstructs/parses the entity JSON merely to obtain revision/time; `session-record-store.ts:42` only diffs these resulting bytes. At tick45, the diff selects the entire191392B entity record +151B atmosphere +8B header for rewriting. At idle86, it selects the entire187969B entity record +151B atmosphere. These are record sizes, not counts of unequal bytes inside each record. Record-diff CPU is tiny; capture and layout are the issue. Durable owner should emit revision-bound metadata/changed records/deletions maintained at native mutation acceptance; keep full capture for checkpoints/recovery and preserve receipt+effect atomicity. Do not remove durability to save work.

4. **Building a view costs about as much as simulating it; query caching stops short of real consumers.** `observation.ts:49` has a per-observation cache, but `:68` calls `session.renderFacts`, whose authored visuals at `session.ts:1297,1304` use fresh direct queries. Multiple Colony visual callbacks repeat reads (`colony.ts:646,651,682`). Probe recorded34 native queries per observation, including hive.lot3× and colony.tree2×. `world.rs:3512` correctly caches Bevy query membership, but each call collects/sorts IDs, materializes values, serializes JSON; `wasm-kernel.ts:633` parses it. A single committed observation read context should serve visuals, inspection, inventories, activities and Whistle; then revision-maintained presentation projections can remove remaining redundant work. No cache may become simulation authority.

5. **Planner output caps do not yet bound discovery work.** `work_candidates.rs:189` scans tasks to determine due work; `:290` clones all pool workers before truncating; `:314` collects/sorts all due tasks then truncates32. `native_work_planner.rs:382` traverses all indexed task IDs to derive designated excavation cells for each window. Process water contributions still scan all IDs for pending/available water (`:966,1003,1021`). These are narrower than scanning all world objects everywhere, but not the plan's claimed charge-by-visited-record budget. Maintain due/dirty queues and small canonical-owner indexes; charge rejected/visited candidates too. Keep the current matcher and route witnesses.

6. **Some 'deep modules' remain split source files with shared Kernel internals.** `native_work_planner.rs:110` is a large lifecycle join: it directly resets field-water vessel state (`:205,268,298`), mutates resource/excavation order status (`:327,360`), acknowledges attempts, and has separate component-type ladders for continuation (`:214`) and requirement collection (`:394`). This keeps domain cleanup knowledge in the scheduler. The prior audit accurately warned that `impl Kernel` moved into child files is not encapsulation. Finish typed domain transition operations returning requirements/results; one Work owner should own attempts and one Materials owner custody/reservations. This is an architectural maintenance finding, not a freshly reproduced physical-law defect.

7. **Existing performance tests establish finite progress, not population capacity.** `colony-performance.ts:46` fixes the workload at50 trees for every population. `colony-performance.test.ts:148` authors200 workers but only asserts some trees complete after90 steps; it does not require200 actors to remain productive. The probe confirms load changes dramatically over time and idle view generation still costs. Future acceptance should report jobs completed, labor/routing/blocked actors over a sustained window, active entities, native search work, capture bytes, observation work, rendering and memory independently. One game-size ceiling needs an explicit workload and latency target, not a smooth-looking idle scene.

## Suggested sequence

1. Stabilize rendering geometry/cache laws with the unchanged art and Pixi, while this read-only cost baseline remains pinned.
2. Join the actual observation callers behind one revision-owned read context; no new authoring abstraction needed.
3. Give canonical record/accounting owners dirty revision journals, incremental record layout and rollback-safe publication; retain transaction/replay proof.
4. Bound scheduler discovery before refining optimizer/pathfinding or increasing population promises.
5. Harden domain transitions and shared cleanup, then expose those same operations through Edmund. Prove a second content consumer via definitions rather than adding another scheduler or executor.

No evidence here supports replacing Pixi, rewriting the simulation again, or declaring all physical laws unsound. The measured weakness is excessive repeated whole-state work and insufficient workload qualification on top of a useful existing native/durable foundation.
