# Renderer source audit: what established engines actually do

Date: 2026-09-23. Scope: source and official documentation review against Hive's existing Pixi world view. This is an architecture finding, not implementation or hosted acceptance. Hive working pin: `dc3168c8` plus the preserved dirty world-view changes in `world-view-repair-20260922`.

## Finding

There is no universal tree that turns a changing voxel world with cut planes, translucent upright art, moving actors, and four camera quadrants into a correct, cheap 2D draw list. The established implementations separate **world storage**, **visible work**, and **paint order**. Their render grouping changes when objects must interleave. Hive currently retains world chunks, then repeatedly flattens and processes the visible picture as one array. That is the costly representation error visible in the source.

The earlier proposal to render an entire 8×8 terrain chunk as one Pixi object is unsound for Hive: neighboring chunks and actors can interleave in isometric depth. The earlier proposal to make each diagonal an independently sorted block was also too strong. A tall sprite may overlap the next diagonal. OpenRCT2 explicitly checks neighboring depth buckets. A bounded paint band may be useful, but its width and overlap rule must be proved on Hive's actual art and geometry.

## Direct comparison

| [Unity isometric Tilemap renderer](https://docs.unity3d.com/2018.3/Documentation/Manual/Tilemap-Isometric-RenderModes.html) | Chunk mode batches tiles as one transparent sort item and is faster, but other sprites cannot interleave inside it. Its own source has a transparency-pass TODO, so it is not proof of perfect art layering. |
| [bevy_ecs_tilemap render settings](https://docs.rs/bevy_ecs_tilemap/0.18.1/bevy_ecs_tilemap/map/struct.TilemapRenderSettings.html) | Chooses render chunk size by change frequency; has Y sorting for isometric layered maps and recommends depth-one chunks for 3D isometric tilemaps. | Rendering chunk size can differ from network chunk size. | [Unreal Paper2D](https://dev.epicgames.com/documentation/unreal-engine/paper-2d-tile-sets-and-tile-maps-in-unreal-engine) / [culling](https://dev.epicgames.com/documentation/unreal-engine/visibility-and-occlusion-culling-reference-in-unreal-engine) | Tile maps are layered; the full 3D renderer culls by bounds and can use depth/occlusion for suitable materials. Paper2D tile-map support is labeled experimental. | Spatial bounds and viewport culling are standard; depth works well for opaque geometry. | Unreal's 3D material/depth pipeline is not evidence that Pixi can automatically sort Hive's alpha images. |
| [Three.js geometry](https://threejs.org/docs/pages/BufferGeometry.html) and [instances](https://threejs.org/docs/pages/InstancedMesh.html) | Geometry exposes groups/draw ranges and instances expose updateable transforms. | GPU buffer retention is a renderer resource technique, not simulation state. | Three.js does not choose correct 2D alpha order or a world streaming contract for the application. |

Gnomoria's original renderer source was not found in an authoritative public repository. [Ingnomia](https://github.com/rschurade/Ingnomia) is an open remake and is cited as such, not as proof of the original game's implementation. Minecraft's proprietary client source was not treated as public evidence; Luanti is the source-inspected open voxel analogue.

## Hive source comparison

Hive already has correct major ownership concepts: an authoritative DO stream, a region cache, per-region derived terrain pictures, a world-view publication barrier, a structural ordering owner, and a GPU batch resource owner. It also already transforms the published Pixi container immediately for pan and zoom.

The actual data flow still defeats retention:

1. [`terrain-picture-owner.js`](../../src/client/terrain-picture-owner.js) retains per-patch body/cover derivatives, then appends every active body and cover to new flat `records`, `exposedFaces`, and `surfaces` arrays and compares the arrays against publication.
2. [`structural-draw-order-owner.js`](../../src/client/structural-draw-order-owner.js) prepares keys for every terrain record, builds dense/base/candidate arrays, and scans the resulting whole view even for a local change. Its physical rules are more specific than generic Y sorting, which is valuable, but its output representation forces whole-view work.
3. [`terrain-face-batches.js`](../../src/client/terrain-face-batches.js) scans the entire ordered list and only reuses a mesh when a whole run has the same key and records. An actor inserted into a long run can split it and cause repacking.
4. [`world-view-owner.js`](../../src/client/world-view-owner.js) starts combined terrain/actor/order jobs. Camera pan/zoom itself is immediate, but newly arrived terrain can trigger another complete picture/order/batch path.

The source therefore supports a narrower statement than “Pixi is slow”: Hive uses a whole-view intermediate representation above Pixi. In the earlier hosted 64×64 run the picture/order phases dominated the measured CPU work; the batch phase was smaller. That run is performance evidence for prioritization, not a guarantee of future frame rate.

## Architecture decision to test, not assume

Keep the world cache keyed by network region. Inside one structural presentation owner, maintain **ordered render bands** keyed by the camera-facing traversal coordinate, with each band made from references to retained per-region records. A band is a render/order unit, not a material-residency unit. Permit an authored object or terrain feature to affect adjacent bands according to checked world bounds. The owner resolves local insertion and exposes one coherent published traversal for Pixi and picking. The batch owner retains buffers for unchanged paint runs; no caller mutates its arrays.

This is an inference from OpenRCT2's bucket/neighbor arrangement, Godot's Y grouping, Unity's interleaving warning, and Hive's own tuple. Its validity for Hive is still unproven. Do **not** immediately add a quadtree: the existing fixed region grid already finds nearby regions, and a quadtree would not solve depth order. A quadtree becomes useful only if measured visible-region selection over much larger worlds becomes costly.

The first implementation gate is small and decisive:

- Same camera/cut, one region arrival: untouched region derivative identities and untouched GPU buffers remain identical; only affected bands repack. The displayed image and picking match a full reference traversal across a region seam.
- One actor moves across a bed/grass/terrain boundary: only its old/new local bands change; support and authored-part order remain correct. No whole-view terrain scan or upload.
- Pan/zoom with unchanged coverage: no terrain derivation, structural rebuild, or buffer upload. Rotation rebuilds the required visible projection/order, without re-fetching resident material. A cut changes only exposed/mown affected pictures and their bands.
- Run the combined hosted DO 64 and 256 scenarios and inspect original-art pixels, frame stalls, time to first usable terrain, completion, and memory. Do not call the representation accepted from isolated unit laws.

If an actual art/geometry witness cannot fit within bounded adjacent-band placement, the structure or authored part must change. Do not silently widen to a global overlap graph or hide the witness with a species/fixture branch. The existing packet's ban on generic overlap graphs remains sensible; its blanket ban on *any* local bounding-box refinement should be revisited only if a concrete Hive witness requires one, since OpenRCT2 demonstrates a bounded neighboring-bucket refinement is a valid game technique.
