# Shared worlds, persistent parties and explicit Draft

[Packet index](README.md) · [Work](01-work.md) · [Release](05-delivery.md)

## Existing gap and chosen split

Public Worker `initializeCore` currently gives every invite holder `${pack}-player`;
outer routing hashes the bearer token into the DO name. Colony has two fixed
worker IDs and selectedWorkers only permits those. RegionProgram.authorize sees
the principal, but execute does not. Fix those real callers; do not add a browser
party registry that the server ignores.

World identity, join invitation, participant credential, game party and socket
are separate. For Colony's new protocol:

- World handle: stable routing identifier, safe to put in the invitation URL.
- Join invitation: a world-scoped secret allowing new participant admission, kept
  in the fragment until explicitly submitted. Not a command credential.
- Participant credential: 32 random bytes generated by browser Web Crypto and
  persisted BEFORE first join, in existing browser persistence keyed by world.
  Stored server-side only as SHA-256 hash. Never put it in share links or observations.
- Principal: `participant:<credentialHash>` host identity local to this world.
  Game code receives an opaque player ID assigned on join, not credential hash.
- Party: canonical game entity owned by that player; people/items/orders refer to
  it. No one-party-per-DO assumption.

Anonymous identity is demo-scoped. Clearing browser storage loses the credential;
this is not reconnect and cannot magically reclaim the old party. Display this
limitation. Normal reload, reconnect, multiple tabs and a lost response reuse the
credential. Do not add passwords, emails, a global identity database or a pretend
account recovery system. Future App customer binding replaces host authentication,
not the game party ownership model.

## Protocol and durable state

Within the existing Colony host, introduce explicit world route segment
`/v2/colony/worlds/:world/{join,observe,command,connect,socket/...}`. Other packs'
existing routes remain their distinct single-controller demo behavior; do not
keep two Colony implementations or silently fall back to old token routing.
Centralize the route parser in `tools/public-engine-host/protocol.ts` with Zod.

```ts
JoinRequest = { invite: string }  // player credential in Bearer; no caller join ID
JoinResult = { player: PlayerId, party: EntityId, people: [EntityId, EntityId] }
SocketAuth = { type: 'authenticate', credential: string }
```

HTTP authorization carries only the participant credential after join. WebSocket
first-message authentication uses that credential; route already selects world.
Origin policy remains exact preview origin. Do not transmit secrets in query
strings, logs or socket handle paths. Frame parsing/size limits remain maintained
protocol limits; do not invent custom recursion checks.

Host table `hive_public_world`: singleton format, world id, pack, invite hash and
existing clock state (reuse current host fields rather than duplicate clock).
`hive_public_participants`: credential_hash PRIMARY KEY, principal UNIQUE,
player_id UNIQUE, party_id UNIQUE. These are authentication-to-game bindings,
not a second people/inventory store. No online/offline flag governs game work.

Join executes under the existing DO owner transaction with the Region dispatch:

```text
join(world, credential, invite):
  hash inputs; verify world's invite and capacity policy
  enter existing serialized DO request/Region lifetime owner
  derive stable participant principal and deterministic join identity
  inside owner transaction:
    re-read participant binding; if found, return existing membership (no spawn)
    resident.begin(current committed revision)
    dispatch host-only joinParty(bindingId) through Region
    if rejected: leave no participant row, people or supplies
    insert participant binding referencing committed party result
  only after both Region dispatch and binding insertion commit: resident.accept
  on either failure: roll back both and discard/invalidate resident
  recompute/re-arm world wake using existing durable wake owner
  return result; publish after commit
```

Membership lookup is idempotent across concurrent HTTP requests using the same
credential. They must still spawn only once.
Use `join:<credentialHash>` as host-derived Region join receipt identity with no
expectedRevision field; caller supplies neither identity nor revision. Never
trust a client-supplied player ID. Avoid detached spawn or side-table writes after
Region commit. If transaction rollback happens, all records and receipt roll back
and the mutated resident is discarded. Existing room/command transaction wrapper
already owns begin/accept/discard; extend it, don't build a second wrapper.

## Principal propagation and command admission

Extend `src/engine/region/index.ts::RegionProgram.execute` with readonly execution
context `{ principal }`, supplied by commitParsed from authenticated dispatch.
Update ALL direct RegionProgram implementations/tests in the same commit. It is
not a command JSON field and cannot be supplied by a player. Do not stash principal
in mutable global state between authorize and execute.

`engine/src/runtime/region-program.ts` resolves participant's opaque player and
party against canonical bindings/current membership and passes a CommandScope to
`GameSession.command` and GamePack command context. For local/browser single-player
use an explicit local-player scope. Existing single-controller packs use explicit
single-owner policy; no missing-scope => omnipotent default.

```ts
type CommandScope =
  | { kind: 'host' }
  | { kind: 'player'; player: PlayerId; party: EntityId };
```

Host-only: step, initial joinParty, global pause/reset and internal physical actions.
Player: named admitted GamePack commands only. Remove public Colony raw ActionRequest
submission. Client movement must invoke scoped Go, not bypass admission through
`kind:'action'`. UI availability uses the same scoped context; dispatch rechecks
current scope. Do not authorize merely because Whistle advertised an operation.

Canonical components: Party(ownerPlayer), PartyMember(party) on people; OwnedByParty
on constructed property, supply containers and orders. Lots derive ownership from
canonical container/holder custody instead of duplicating a mutable owner field on
every split portion. Domain outcomes that create loose job output assign ownership
at the output container from originating order. Neutral wild trees/terrain can be
worked by any party unless already exclusively claimed by a conflicting active
world operation. Competing edits serialize and reject stale physical targets.

Permission primitive: `mayControl(scope, entity)` and `mayUseMaterials(scope, owner)`
query canonical membership/ownership; no display names, hardcoded worker arrays
or UI selection trust. Work candidates require same permitted party; native
beginAttempt/material admission rechecks. All server simulation systems may advance
all parties; their host privilege must not erase the task's party scope when they
submit a physical operation. No cross-party material use by a host-authored haul.
First slice has no implicit co-op delegation. Leave an explicit permission seam,
not an unused grants framework. Sharing world invite allows a NEW party, not control
of existing parties. Inspect others' public people/work without their credentials.

## Spawn and current Colony callers

Extract `colony.ts` fixed two-worker startup into `createColonyParty(player, party,
spawn)` content factory. IDs derive from party identity, e.g. `party/<id>/person/0`
and `/1`; names/looks come from existing definitions. Two playable people, not the
cat or guest. Other neutral world inhabitants remain world-owned once, not per join.
Starter supplies/pails follow one explicit current content recipe; no magic new
pails during hauling and no duplication on reconnect. Remove preplaced worker jobs
that assume global pantry/lumber IDs; create party supplies and any starter intent
through the same factory and normal definitions.

Spawn selection: deterministic bounded search around existing safe starting area,
using actual terrain/traversal and occupied spawn contacts. Both people and their
starter storage must fit, have valid support/headroom, and be reachable as intended.
Prepare the whole result before mutation. If no suitable region/capacity is
available, return `spawn-unavailable` with no partial party. Do not generate the
whole world or stack players in a blocked fixture. Content seed remains world seed.

Audit all fixed `workers` arrays, subjects, selectedWorkers, selectedDigWorker,
needs/tasks/material factories, performance fixtures and observation selection.
Derive actors from PartyMember + capability queries, then permission. No permanently
parallel 'old two workers' path for Colony. Performance demo explicitly creates its
synthetic party/population through the same factory capabilities; it isn't public
join authority.

## Draft UI, disconnect and ticking

Expose Draft and Undraft beside selected owned people in existing bottom action
bar and command catalog. WorkParticipation remains one source for control mode;
name its semantic states explicitly if converting boolean. Selected is client UI
state, Draft is durable game state. Go requires Draft and does not secretly change
mode. Undraft stops that attempt's manual route through the native movement owner,
then returns the actor to work discovery; it does not erase cargo or progress.
Mixed selection commands affect only admitted owned actors; reject unauthorized
members explicitly rather than silently applying a misleading partial operation.

Socket close does not mutate Draft, orders, membership or people. Keep current
WORLD lease/wake/sleep policy: B's activity keeps the same world running and A's
people work normally. Do NOT change to 'every retained party keeps its DO alive
forever'. When the world sleeps, existing policy applies to the whole simulation;
no offline catch-up is added here. Rejoin renews world activity and observes the
same existing people. Test multiple tabs/disconnects against this exact behavior.

## Dynamic native spawn and transactional binding details

Current createAuthoredEntity is not permission to create native Body/Container
components. Add a host-only party spawn operation backed by the native entity
registry's existing definition/component validation, not arbitrary player entity
JSON. GamePack provides the two-person/starter-content template; validated host
join selects it and spawn poses. Prepare all native entities, canonical party/
member/ownership components and authored starter intent as one bounded group.
Validate IDs, schema, references, quantity/capacity and terrain before insertion.
A rejected group inserts nothing. Native IDs derive from an opaque world-local
player ID; do not put credential hashes in entity IDs or broadcast them.

World-local player/party counter lives in canonical Region/session game state,
allocated in join candidate. Thus host participant row, game membership, two people
and supplies can commit in one owner transaction. The host dispatch input is
`{kind:'join-party', credentialBindingId}` with a host-derived opaque binding ID;
player id is allocated inside the candidate and returned. Derive bindingId as
SHA-256 of the world ID, fixed domain separator and credential hash so a retry
reconstructs identical command bytes; never generate new random command fields
on retry. Binding IDs are internal admission data, excluded from observation. The credential hash
stays in the host table. Only host principal can invoke join-party. An existing
binding row returns its existing result on every subsequent join request. No
pre-allocation outside transaction that could orphan a membership.

The game retains Party(ownerPlayer), PartyMember(party), OwnedByParty(party) as
canonical components. Host table binds authenticated principal to playerId and
partyId; cross-check these against game membership on admission. If they disagree,
fail closed as corrupted relationship rather than creating a replacement party.
Pass the authenticated execution context through RegionProgram -> resident.execute
-> applyCommand -> GameSession.command -> command context explicitly. Pure command
schema parsing must not read ambient principal. Host-only join operation should
use the same transaction/resident path as any admitted world edit.

## Physical action scope is retained until admission

The current pendingActions array contains raw ActionRequest; it must become
`ScopedAction { scope: host | party(PartyId), request: ActionRequest }` in the same
Session/native format change as this packet. Session injects scope from trusted
CommandContext or native WorkAttempt, never from player JSON. Pending actions and
native dispatch retain that scope through save/reload and final execution.
Party-scoped material/structure actions use one native ownership predicate on
source/destination/target; a previously admitted command cannot spend another
party's items if ownership changed before its queued effect executes. Host-only
spawn/clock/config operations have explicit host scope. A provider's ability to
run during the host tick does not make its work action host-scoped. Native
executeAttempt derives party from canonical attempt instead of accepting another
party in the inner action. Update contracts/actions/record codecs and fixtures in
one joined change; no optional absent-scope privilege.


World creation/routing is deterministic: for this invite-based demo generate a
32-byte invite secret client-side and set worldHandle=SHA-256(invite). Route the
Colony namespace to `REGIONS.idFromName("colony-party-v1:" + worldHandle)`.
The DO verifies its own ID and stored worldHandle/pack on every initialization;
join verifies invite hash equals handle. First valid join may initialize the empty
world through existing initialization, but people/supplies/binding still commit as
one join. Other endpoints never implicitly create a participant. A failed join
may leave an initialized empty world, never half a party. Preserve the invite as
world access/join capability only; a random handle is not authentication.

Update the principal signature chain in one patch: RegionProgram.execute ->
createSessionRegionProgram.execute -> SessionResident.execute -> applyCommand ->
GameSession.command -> command.invoke. All tests/custom RegionProgram consumers
compile with the explicit readonly principal context. Reject player pause/resume/
reset and raw-action commands at BOTH HTTP boundary and direct Region authorization.
Inject forged player/party/scope fields to prove they cannot override context.

The join preparation validates native spawn records AND authored starter records
and their cross-references before publication. Inject failure after native candidate
spawn and before authored validation, and after Region dispatch before participant
INSERT; reopen same SQLite database. Assert unchanged revision, no join receipt,
no binding, no party/member IDs, no starter lots for failed transaction. After a
successful commit with dropped reply, assert exactly one binding/party, exactly two
member IDs, exact starter quantities and a single replayed receipt. Different
simultaneous client requests for the same credential receive the same membership;
the serialized in-transaction read is required even if a preflight read was made.
